# Echo Show 5 1st gen with Hermes Voice — 2026-11-05

**Question.** Can an Echo Show 5 1st gen run Hermes Voice the same way the Echo Dot 2 does (echo-dot-assist,
a "Hey Hermes" wake word, Home Assistant, a Hermes profile), and what does it take?

**Answer.** Yes. It took about two hours from a factory-reset Show to a working voice assistant, most of it
waiting. Two things went wrong on the way (a false unlock, disk space) and both are now documented. The
step-by-step guide is [devices/echo/README.md](../../devices/echo/README.md#echo-show-5-1st-gen-on-an-ubuntu-live-usb);
this log is the record behind it.

## Setup

| Item | Value |
|---|---|
| Echo | Echo Show 5 1st gen, model H23K37 (`checkers`), bootloader build `44072a3-20240709_170103`, factory reset, never on Wi-Fi |
| PC | ThinkPad (the one that flashed the Dot from Windows), booted from an Ubuntu 26.04 live USB stick |
| Work drive | 8 GB USB stick, ext4, on a USB-C hub (the PC has two USB-A ports) |
| Control | The setup was driven over SSH from a Mac, inside tmux on the PC |
| echo-dot-assist | main at `ae2e3ef` cloned, release tag `v2026.11.05.000019-beta` used (below) |
| Unlock | amonet-checkers v2.0.1 (R0rt1z2) |
| Firmware | Fire OS 6574.1, NS65741/8149 (`0013222532484`) |
| Home Assistant | 2026.10.4 in Docker Desktop on macOS; speech: Wyoming faster-whisper and Piper |

## What happened, in order

1. **Live session out of disk.** The live session's writable layer is RAM-backed (7.3 GB here, about
   5.5 GB free). Work has to live on a separate drive.
2. **The setup downloaded the Android NDK and filled the disk** (`write error (disk full?)` while unpacking).
   *Cause:* the cloned commit had no release build on GitHub yet, so the setup builds from source without
   asking. *Evidence:* the setup's `prebuilt_tag` found no tag for HEAD; the commit touched
   `scripts/lib/device.sh`, which the setup counts as part of the Echo's build. *Fix:* check out the newest
   release tag, carry over that commit's two PC-side files, mark them `git update-index --assume-unchanged`;
   the setup then offered "Use it (recommended): nothing to compile".
3. **The spare drive was FAT, not ext4**, after formatting in the Disks app. Reformatted with `mkfs.ext4`.
4. **Mount path:** this Ubuntu mounts drives under `/run/media/$USER/`, not `/media/$USER/`. Over SSH,
   `udisksctl mount` needs a desktop session; `sudo mount` works.
5. **Two USB ports for three devices.** The live stick cannot be removed (it runs the OS). The work drive
   moved to a hub after `adb kill-server` (the setup's adb server kept it busy) and `umount`.
6. **Fastboot:** Volume −, Volume + and Mute held while plugging in power → Amazon logo with "FASTBOOT mode".
   (echo-dot-assist's setup text says "camera shutter"; amonet says Mute, and Mute worked.) USB `0bb4:0c01`.
7. **First unlock: reported success, did nothing.** amonet printed "Exploit most likely successful!" and the
   Show rebooted into Amazon's setup. Volume + at power-on gave the stock recovery error screen (Echo logo,
   red triangle). *Evidence:* `fastboot getvar unlock_status` → `false`. *Why:* amonet prints success when
   `fastboot flash brick` times out (exit 124) and never checks afterwards. Nothing had been written.
8. **Second unlock: worked.** Same cable, port and payload a few minutes later; the Show dropped off USB and
   came up in TWRP by itself. Other owners with this bootloader build report the same flakiness on the XDA
   thread; the author's advice is retrying and USB 2.0 ports.
9. **Firmware:** the Show came out of the unlock on build `0013222532996`; the setup replaced it with 8149.
10. **Disk space, again.** Unpacking the system image peaked at about 6.7 GB (firmware 1.37 GB,
    `system.new.dat` 2.57 GB, `system.img` about 2.6 GB of data, plus the repository) on a drive that holds
    7.1 GB once formatted. It fit only after the firmware file was moved to RAM mid-run (copied, checksum
    checked, replaced by a symlink). *Conclusion:* the guide now says 16 GB.
11. **Writing the system partition:** 49 chunks of about 66 MB, about 30 minutes (about one chunk a minute at
    first, faster later) over a slow stick (about 2.5 MB/s writes).
12. The rest ran unattended: boot image, release build, firmware probe, hassmic, lockdown, Alexa off, Wi-Fi,
    install. Kiosk Satellite was installed when offered, later removed (below).

## Home Assistant and Hermes

- **Adding it:** ESPHome by IP, port 26053 (no discovery from Docker Desktop on a Mac, same as the Dot);
  "Allow the device to perform Home Assistant actions" ticked as the setup asks. The wake word slot came up
  as "Alexa".
- **First voice test** ("Alexa, what time is it?"): Hermes searched the web for the time and could not read
  it. *Cause:* Hermes has no clock, and time pages show the time only in a browser. *Decision* (user): both
  of (a) hermes_voice sends Home Assistant's local date and time on every turn, and (b) the pipeline prefers
  local handling, so Home Assistant answers time, timers and device commands itself.
- **Time zone:** the first local answer said 9:53 PM at 3:53 PM. *Cause:* the skill's onboarding left a new
  Home Assistant on UTC. *Fix:* `ha_setup.py` sets the computer's time zone on onboarding.
- **"Hey Hermes":** after uploading the model on the Show's settings page (both volume keys stand in for the
  action button), the Show answered to nothing. *Cause:* the upload replaces "Alexa" and leaves the wake
  word slot empty. *Fix:* pick "Hey Hermes" in Home Assistant; now step 5 of the wake word guide.
- **Date question** ("Hey Hermes, how many days until Christmas?"): answered by Hermes with the right date.

## Screen

Kiosk Satellite (a Home Assistant dashboard) was removed: the user wants the screen for the agent, not home
control, and its admin page was open to the network without a password. The face came back. The agent screen
that replaced it has its own log: [2026-11-05-hermes-screen.md](2026-11-05-hermes-screen.md).
